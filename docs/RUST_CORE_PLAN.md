# Rust core: river solver + MCCFR trainer

Branch `rust-core`. Goal: move the two compute-bound parts of AllIn — the live
**river subgame solver** and the **blueprint MCCFR trainer** — into Rust
(`backend/core-rs`, Python module `allin_core` via PyO3/maturin), so that

1. river solves converge well inside the serving budget (today a deep-stack
   river tree needs ~9 s for 400 iterations even on an M6; prod's budget is 8 s
   on a fractional vCPU, so those solves are truncated), and
2. training is fast enough on a laptop (Apple M6, 12 cores, 32 GB) to afford a
   **bigger abstraction** (SPR buckets, finer flop/turn buckets) and the
   iterations it needs.

Everything else stays Python: Flask API, `GameSession`, range tracker,
exploitation, guards, the evaluation harness (for now).

## Principles

- **Python is the oracle.** Every Rust component must match the Python reference
  on golden fixtures before it is used anywhere. No component is "done" on
  vibes or on a benchmark alone.
- **Port first, then change the abstraction.** While both sides implement the
  same abstraction, any difference is a bug. Changing buckets during the port
  would make a different blueprint uninterpretable (port bug or abstraction?).
- **Feature-flagged adoption.** Serving switches per component
  (`ALLIN_RIVER_BACKEND=python|rust`), so prod can always fall back.
- **No silent tolerance creep.** Discrete outputs are exact; river floats are
  `rtol=1e-9`. Loosening a tolerance requires a progress-log entry saying why.

## Layout

```
backend/core-rs/
  Cargo.toml, rust-toolchain.toml (pinned 1.99.1), pyproject.toml (maturin)
  src/lib.rs        pure-Rust core; PORTED = components that pass parity
  src/python.rs     thin PyO3 layer (feature "python"); `cargo test` runs without Python
  parity/           pytest harness: allin_core vs fixtures (+ python_shim.py)
  bench/            bench_baseline.py -> bench/python_baseline.json (git-ignored)
  fixtures/         generated by backend/bot/scripts/export_rust_fixtures.py (git-ignored)
```

The API contract each component must expose is written at the top of each
section of `parity/test_parity.py`; `parity/python_shim.py` implements the same
contract with the Python code (executable documentation).

## Commands (from the worktree root)

```bash
# one-time: Python 3.12 venv (matches the Docker image)
uv venv -p 3.12 .venv && uv pip install -p .venv/bin/python -r backend/requirements-dev.txt maturin

# fixtures (deterministic; --quick for a fast loop, --only to regenerate one group)

# perf
../../.venv/bin/python bench/bench_baseline.py   # Python baseline -> bench/python_baseline.json
../../.venv/bin/python bench/bench_rust.py       # Rust river, same spots, prints speedup

```

Git-ignored assets (baked postflop tables, blueprints) are symlinked into the

## Phases

| # | Phase | Components | Gate |
|---|---|---|---|
| 0 | Scaffold + oracles | crate, fixtures, harness, baseline | ✅ harness 9/9 vs Python; mutation-tested |
| 1 | River solver | `river_showdown`, `river_tree`, `river_cfr`, `river_gadget` | ✅ core: parity green (exact mode bit-identical), 7× measured. ⬜ serving: `ALLIN_RIVER_BACKEND` adapter + Docker Rust stage + local A/B |
| 2 | Evaluator + bucketing | `eval_rank7`, `buckets` (preflop map; flop/turn `.npy` table lookup; river runtime equity + canonical-board cache) | ✅ exact on all fixtures (strict parity green); rank7 10×, river board 470× cold |
| 3 | Betting engine + keys | `engine` (state-threaded, both menu modes), `keys` | exact on all fixtures |
| 4 | Single-thread MCCFR + SQLite writer | `mccfr` (fixture TBD) | table identical to Python for N iters under a shared injected uniform stream |
| 5 | Parallel trainer (M6) | shared table, all cores | BR/LBR matches a Python run at equal iterations; throughput measured |
| 6 | Abstraction upgrade | SPR buckets, finer buckets | user signs off the spec |
| 7 | Long run + v3 bundle | train, re-bake, re-fit opponent models | BR/LBR + human-like match; user approves cutover |

Phases 1, 2, 3 are independent (can run in parallel sessions/worktrees);
4 needs 2+3; 5 needs 4.

### Phase 1 notes (river)
- Two arithmetic modes (`exact=False` default):
  - **exact** replays numpy 1.26's operation order (`bincount`, `cumsum`,
    pairwise `sum`; row sums over < 8 actions are left-to-right) and is
    **bit-identical** to Python. It is the parity gate.
  - **fast** (served) differs only in the showdown kernel (per-card prefix
    sums, O(H), shared actor-side terminal stats). Kernel within 1e-9; CFR
    trajectories within 1e-9 except on exact ties (see the progress log).
  - Prod pins numpy 1.26.4; a numpy upgrade could change its reduction order and
    break exact-mode bit parity (regenerate fixtures and re-check).
- Rust takes `raw/c1/c2` from Python initially (`build_board_arrays` stays in
  Python until Phase 2 provides the evaluator); the dense groups `g/G` are
  derived in Rust from `raw`.
- Internal tables are action-major `[A][H]`; the API speaks Python's `[H, A]`.
- Mirror the Python `RiverCFR` API so `solve_control.py` (`solve_river`,
  `solve_river_gadget`, EV gate, `reach_into`, `node_action_values`,
  `warm_start`) can drive either backend unchanged. Those extra methods need
  fixtures added before they're swapped in.
- `inject_realized_edge` (off-grid edges spliced into the tree) is used by the
  served solver — needs tree fixtures with injected edges.

### Phase 4 notes (training parity)
- MCCFR samples opponent actions with `random.choices`; cross-language bit
  parity needs a Python "reference mode" that draws from an injected uniform
  stream with an inverse-CDF both sides implement identically.
- `InformationSet.get_strategy` uses numpy's `.sum()` (pairwise, 8-way unrolled
  for ≥5 elements). An ULP difference flips sampled actions and diverges the
  trajectory (see memory: trainer-perf-improvements). Exact mode must reproduce
  numpy's reduction order; otherwise validate statistically (BR/LBR) instead.
- Keep the DB schema identical so serving reads Rust-trained blueprints unchanged.

### Phase 6 notes (abstraction)
- History: SPR buckets were once decided against (1.7–2.5× training for ~9% of
  decisions low-SPR); ROADMAP item 8 later revived turn-only SPR buckets
  (<2 / 2–4 / 4–8 / >8). The speedup removes the cost objection; the value
  question still needs measuring (per-line BR/LBR + human-like match).
- Touches: `keys.py` (both languages, one fixture), centroids + baked tables,
  opponent-model re-fit (the abstraction guard self-disables exploit on
  mismatch), `/api/abstractions` + KeyExplorer dropdowns (frontend — needs
  explicit go-ahead).

## Risks
- Docker/CI: the image needs a Rust build stage (or prebuilt Linux wheels).
- AGPL: b-inary/postflop-solver is AGPL — read for ideas, never copy. robopoker
  (MIT) is safe to borrow from.
- Scope creep: porting the evaluation harness (BR/LBR) is optional and later.

## Baseline (M6, 2026-11-08) — `bench/python_baseline.json`, `bench/rust_river.json`

| What | Python | Rust fast | Rust exact |
|---|---|---|---|
| River CFR, 194 decision nodes (pot 12 / stack 194) | 22.9 ms/iter → 9.1 s per 400 | 3.27 ms → 1.31 s (7.0×) | 6.3 ms |
| River CFR, 106 nodes (30 / 185) | 12.4 ms/iter → 5.0 s | 1.77 ms → 0.71 s (7.0×) | 3.4 ms |
| River CFR, 24 nodes (80 / 160) | 2.7 ms/iter → 1.1 s | 0.38 ms → 0.15 s (7.1×) | 0.74 ms |
| Gadget / exploitability | ≈ CFR per iteration | 7.1× / 7.5× | |
| `build_board_arrays` (river only) | 0.05 s | (Phase 2) | |
| `rank7` | 1.28 M/s | 12.8 M/s via `rank_batch` incl. numpy marshalling (10×) | |
| River buckets, one board × 1081 hands (`bench/bench_buckets.py`) | 45 ms | 0.095 ms cold / 0.009 ms cached | |
| Flop / turn bucket lookup | 73 k/s / 68 k/s | 6.4 M/s / 1.8 M/s | |
| Training, capped, single core (early run) | 227 it/s | (Phase 4) | |

The river solver was already numpy-vectorized, so ~7× is the honest ceiling of a
straight port (per deep-tree iteration: ~2 ms showdown kernels, ~1.2 ms node
updates). The trainer is pure interpreter overhead and should gain far more.

### 2026-11-08 — Phase 1 core: river solver ported
- `src/river/{showdown,tree,cfr}.rs` + bindings (`showdown_measure`,
  `compatible_mass`, `river_tree_nodes`, `RiverCFR` incl. `run_gadget`).
  `PORTED` = the four river components.
- **Exact mode is bit-identical to Python** on every river fixture: 20 boards ×
  3 kernel cases, 16 trees, 6 CFR + 4 gadget cases at 1/10/50 iterations
  (regret, average strategy, values, exploitability, gadget regret).
- **Why two modes (comparison semantics changed, recorded per the rule):** the
  first fast-mode run failed parity on the both-uniform case. Root cause: with
  symmetric ranges many action values tie exactly; the ~1e-11 float noise in
  the regrets crosses the 1e-12 regret-matching threshold, so CFR+ breaks ties on
  noise and the trajectory forks (Python's own path there is noise-determined
  and would change with any reordering, even inside numpy). So parity is now:
  exact mode = bit equality (stricter than before); fast mode = kernel at 1e-9,
  CFR at 1e-9 on non-degenerate reaches (all pass at ~1e-12), and on the
  both-uniform case exploitability within 2% (observed 0.5% at 50 iters).
- Speed: 7.0–7.5× over Python on all three benchmark trees (table above). Deep
  river (194 nodes) 400 iterations: 9.1 s → 1.3 s.
- Not done in Phase 1 yet: the serving adapter (`ALLIN_RIVER_BACKEND`), which
  needs `RiverCFR.from_tree` (Python tree incl. injected edges), `reach_into`,
  `node_action_values`, `warm_start`, `_eval`/`_br_value` with blueprint
  strategy tables, a Rust build stage in the Docker image, and a local A/B.

### 2026-11-08 — Phase 2: evaluator + bucketing ported
- `src/eval.rs` (`rank`, `rank_with`, `rank_batch`, `validate_row`): Cactus-Kev
  class values (= phevaluator), per-suit 13-bit masks + multiplicity masks +
  colex ranks; all tables `const`. Unit tests: exhaustive 2,598,960 5-card hands
  and 500k random 6- and 7-card hands vs an independent brute-force (best of
  C(k,5) subsets, classes enumerated and sorted). Every class reached.
- `src/buckets/`: `preflop` (maps derived from the generated
  `preflop_equity.rs` exactly as `_quantile_buckets`: stable sort, dict order
  breaks ties, float `int(i*n/169)`), `canonical` (24 perms in itertools order,
  suits compared as LETTERS `C<D<H<S` like Python's tuples, encoded by deck
  index `HDCS`), `npz` (stored-zip + npy reader, bounds-checked, rejects
  compressed/oversized/truncated/unsorted/out-of-range), `sha1` (centroid
  stamp), `cache` (sharded `Mutex` LRU, `Arc` values, compute outside the lock;
  `Send + Sync`), `mod.rs` (`Buckets`: lazy `OnceLock` tables, stamp check =
  `_verify_stamp`, a mismatch is a hard error; river = `board_winrates` with
  integer win/tie counts then Python's `rint((w + 0.5 t)/990 * 1980)`).
  Bindings in `src/py_buckets.rs`: `rank_batch`, `preflop_buckets`,
  `fine_to_coarse`, `Buckets(dir, river_cache_boards=None)` with
  `situation_ids`, `bucket_batch`, `preload`, `n_buckets`, `river_cache_info`,
  `clear_river_cache` (GIL released; bad input = `ValueError`).
- **Parity: exact on every fixture** (strict mode): 300k rank rows (5/6/7),
  1326 preflop combos, 20k flop + 20k turn + 2400 river situations (ids and
  buckets). Extra ad-hoc check: all 1081 hands on 300 random river boards
  (324,300 situations) identical to `PostflopV2.bucket`.
- numpy order reproduced in `Centroids::assign` (EMD = sequential `cumsum`,
  `abs`, pairwise `sum` via `river::showdown::np_sum`; first-minimum argmin).
  The river bucket depends only on the integer equity numerator (0..=1980), so
  the 1981-entry numerator→bucket map is precomputed with that exact code.
- Deviation (semantic, recorded): Python falls back to Monte Carlo
  `equity_distribution` (its own RNG) on a flop/turn table miss or a missing
  table; Rust returns an error instead (not reproducible across languages; the
  shipped tables hold every canonical flop/turn situation). The `.npy` extracts
  (`ALLIN_MMAP_POSTFLOP`) are not read — the `.npz` is stored-uncompressed, so
  loading both tables takes ~45 ms. The river cache is per `Buckets` instance
  (share one across threads), not process-global like `_RIVER_BOARD_CACHE`.
- Bench (`bench/bench_buckets.py` → `bench/rust_buckets.json`): rank7 12.8 M/s
  (10× Python, batch API incl. marshalling); one river board × 1081 hands
  0.095 ms cold / 0.009 ms cached vs Python 45 ms; flop/turn lookups 6.4 / 1.8 M/s
  vs ~70 k/s.
- Pure-Rust entry points for other phases: `crate::eval::rank(&[u8]) -> i32`,
  `crate::eval::rank_with`, `crate::buckets::fine_to_coarse() -> &'static [u8; 169]`,
  `crate::buckets::preflop_buckets`, `crate::buckets::Buckets::bucket`.
